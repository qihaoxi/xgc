# 08 — 弱引用与终结器

> 工业级 GC 必须正确处理弱引用（weak reference）和终结器（finalizer）的交互。这两个机制看似简单，实则是 GC 正确性的重灾区。

---

## 1. 弱引用

### 1.1 定义

弱引用是一种**不阻止对象被回收**的引用。如果对象仅通过弱引用可达，GC 可以回收它。

### 1.2 xgc 中的接口设计

```c
// include/xgc/gc_types.h 中增加：
enum {
    GC_OBJECT_FLAG_WEAK_REF = 1u << 2,  // 已存在
};

// 弱引用 slot 标记（通过 descriptor flags）
enum {
    GC_DESC_FLAG_HAS_WEAK_SLOTS = 1u << 3,  // 新增
};

// descriptor 回调增加弱引用遍历：
typedef void (*gc_trace_weak_slots_fn)(gc_header* obj, gc_visit_slot_fn visit_weak, void* ctx);
```

### 1.3 GC 处理弱引用的时序

```
collect_full:
    Phase 1: Mark — 只通过强引用（trace_slots）遍历
    Phase 2: 处理弱引用
        for each object with HAS_WEAK_SLOTS:
            desc->trace_weak_slots(obj, clear_dead_weak_callback, ctx)
            // callback: if *weak_slot 指向未标记对象 → *weak_slot = NULL
    Phase 3: Finalize + Sweep
```

**关键不变式**：弱引用**不能**延长对象的生命周期。mark 阶段不追踪弱引用指向的对象。

### 1.4 弱引用与 moving GC 的交互

如果弱引用指向的对象被移动了（copying/compacting）：
- 如果对象存活 → 更新弱引用 slot 到新地址
- 如果对象死亡 → 清空弱引用 slot 为 NULL

### 1.5 实现文件

```
src/core/weak.c（新建）
├── gc_process_weak_references(rt)  — GC 阶段 2 调用
├── gc_weak_slot_is_alive(rt, obj)  — 判断弱引用目标是否存活
└── gc_clear_dead_weak_slots(rt)    — 清空死亡目标的弱 slot
```

### 1.6 测试要点

```c
// tests/test_weak_ref_substrate.c
// 场景 1: 弱引用目标存活 → slot 不变
// 场景 2: 弱引用目标死亡 → slot 被清为 NULL
// 场景 3: 弱引用 + moving GC → slot 更新到新地址
// 场景 4: 循环中只有弱引用 → 环被回收
```

## 2. 终结器（Finalizer）

### 2.1 定义

终结器是对象被 GC 回收**之前**调用的清理函数（如关闭文件、释放原生资源）。

### 2.2 终结器的陷阱

| 问题 | 说明 | 解法 |
|------|------|------|
| **复活（Resurrection）** | finalizer 中把 `this` 重新挂到活对象 → 对象不该被释放 | 终结后重新标记，下一轮再回收 |
| **终结顺序** | A→B，A 和 B 都有 finalizer，先终结谁？ | 拓扑排序或不保证顺序 |
| **终结器中分配新对象** | finalizer 调用 gc_alloc | 必须允许，但不能触发新的 GC |
| **终结器抛出异常** | C 中没有异常，但 finalizer 可能 crash | 容错包裹 |

### 2.3 两阶段终结模型（推荐）

```
Phase A: Mark（正常标记）
Phase B: 找出"不可达但有 finalizer"的对象
    → 这些对象不立即释放，而是放入 finalization queue
    → 重新标记它们及其子图为存活（防止子对象被误释放）
Phase C: Sweep（只释放"不可达且无 finalizer"的对象）
Phase D: 执行 finalization queue（在 GC 完成后）
    → 调用 finalizer
    → 下一轮 GC 再判断对象是否真正可回收
```

### 2.4 数据结构

```c
// gc_internal.h
typedef struct gc_finalization_queue {
    gc_header** items;
    size_t      count;
    size_t      capacity;
} gc_finalization_queue;

// gc_runtime 中增加：
struct gc_runtime {
    ...
    gc_finalization_queue finalize_queue;
};
```

### 2.5 实现文件


## 3. 引用强度层级（soft / weak / phantom）

工业级运行时（JVM 是范本）的引用强度是一条**有序链**，不止"强 + 弱"两级。xgc 用一个 `strength` 枚举统一处理，GC 在标记完成后**按强度从强到弱分级处理**：

```c
typedef enum {
    GC_REF_STRONG  = 0,   // 普通引用，参与可达性，绝不被 GC 清除
    GC_REF_SOFT    = 1,   // 软引用：仅在内存压力下才清除（缓存语义）
    GC_REF_WEAK    = 2,   // 弱引用：只要不再强可达就立即清除
    GC_REF_PHANTOM = 3,   // 虚引用：对象回收后用于"已回收"通知，get() 永远返回 NULL
} gc_ref_strength;
```

### 3.1 处理顺序（关键，顺序错会导致语义错误）

GC 在 mark 完成、sweep 之前，按下列顺序逐级处理。每一级处理后，该级引用的目标若没有更强的引用维持，就降级为"本级可清除"：

```
mark 完成（强可达对象全部标黑）
  │
  ├─ 1. 处理 SOFT：若本次为高内存压力（见 §3.2），把"仅软可达"对象视为不可达
  │       否则保留（软引用此轮存活）。决定后，被清的软对象的 referent slot 清 NULL
  │
  ├─ 2. 处理 WEAK：所有"仅弱可达"对象的 weak slot 一律清 NULL
  │
  ├─ 3. 处理 finalizer：仅弱/软可达但带 finalizer 的对象进 finalize queue（复活窗口，见 §2.3）
  │       —— 注意：finalizer 可能复活对象，所以必须在 phantom 之前
  │
  └─ 4. 处理 PHANTOM：对象确定不可达且已 finalize 完毕后，把虚引用入"已回收通知队列"
          虚引用的 referent **不**通过 get() 暴露（防止复活），仅用于通知 VM 做善后
```

> **为什么 soft 在 weak 之前、phantom 在最后**：强度越强越晚被清除。soft 比 weak 强（压力小就留），phantom 最弱（连 get 都不给，只在对象彻底死亡后通知）。finalizer 夹在 weak 和 phantom 之间，因为它有复活能力——若放在 phantom 之后，已发出的"已回收"通知就可能被复活打脸。

### 3.2 软引用的清除策略（内存压力驱动）

软引用是**缓存**语义：内存宽裕时全留，吃紧时按 LRU 清。复用文档 12 的三级压力模型：

```c
// 软引用是否在本轮被清除
int gc_soft_should_clear(gc_runtime* rt, gc_soft_ref* ref) {
    gc_pressure_level p = gc_current_pressure(rt);   // 见文档 12 §4.1
    if (p >= GC_PRESSURE_HIGH) return 1;             // 高压：全清
    if (p == GC_PRESSURE_MEDIUM) {
        // 中压：按"上次访问距今"清除老的（类似 JVM 的 SoftRefLRUPolicyMSPerMB）
        uint64_t idle_ms = gc_now_ms() - ref->last_access_ms;
        return idle_ms > rt->config.soft_ref_idle_threshold_ms;
    }
    return 0;                                         // 低压：全留
}
```

> 软引用 referent 每次经读屏障（公共入口 `gc_load_ref` → 并发算法的 `read_barrier`/`gc_read_ref` 实现，见 20 §4.1）成功读取时刷新 `last_access_ms`（在读屏障慢路径里顺带更新，或由 VM 显式调用 `gc_soft_touch`）。

### 3.3 与 moving GC 的交互

soft/weak/phantom 的 referent slot 都和普通弱引用一样：**不参与正常 trace**，但若对象因更强引用而存活且被移动，这些 slot 必须在 §3.1 处理时**一并更新为新地址**（用文档 20 的 forwarding 解析）。顺序：先更新（对存活的）、再清除（对不可达的）。

## 4. 弱引用 + 终结器交互矩阵

| 对象状态 | 弱引用 slot | finalizer |
|---------|------------|-----------|
| 强可达 | 保持 | 不调用 |
| 仅弱可达 + 无 finalizer | 清 NULL | — |
| 仅弱可达 + 有 finalizer | 保持（对象进 finalize queue） | 入队 |
| finalize 后仍不可达 | 清 NULL | 不再调用 |
