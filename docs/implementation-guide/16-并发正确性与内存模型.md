# 16 — 并发正确性与内存模型

> 超高速多线程 GC 的正确性建立在精确的内存模型之上。本文件用 happens-before 关系和 C11 内存序,形式化论证 mutator 与 collector 并发时的安全性。**这是最容易出错、最难调试的部分,必须严格遵守。**

---

## 1. 为什么需要内存模型

多线程 GC 中,mutator 线程和 collector 线程同时读写共享数据(对象图、标记位、颜色)。在弱内存序的 CPU(ARM/POWER)上,没有正确的同步原语,会出现:

- collector 看到对象的旧引用值 → 漏标活对象 → use-after-free
- mutator 看到对象的部分初始化状态 → 读到垃圾指针
- 标记位的写入对其他线程不可见 → 重复标记或漏标

**单线程(GC_MULTITHREAD 未定义)不存在这些问题** — 所有原子退化为普通操作,顺序由程序顺序保证。本文件只针对 `GC_MULTITHREAD` 启用的场景。

---

## 2. 共享数据的同步分类

| 共享数据 | 读者 | 写者 | 同步要求 |
|---------|------|------|---------|
| `gc_state` | 所有 mutator(poll) | 协调员 | acquire/release |
| 对象的引用 slot | mutator + collector | mutator(store_ref) | 写屏障 + 内存序 |
| mark bit / color | collector | collector + mutator(barrier) | 见 §4 |
| `rc` 计数 | collector | mutator(retain/release) | relaxed + dec 时 acquire |
| 全局对象链表 head | collector | mutator(alloc) | CAS acq_rel |
| `safepoint_arrive_count` | 协调员 | mutator | acquire/release |
| forwarding 指针 | mutator(read_barrier) + collector | collector | acquire/release |

---

## 3. 核心 happens-before 关系

### 3.1 对象初始化 → 发布

**问题**:线程 A 分配对象 O 并初始化其字段,然后把 O 的指针写入共享 slot。线程 B 读到这个指针后访问 O 的字段。必须保证 B 看到的是初始化后的字段,不是垃圾。

```c
/* 线程 A */
O = alloc();
O->field = X;              // (1) 初始化
gc_store_ref(rt, t, owner, slot, O);  // (2) 发布,内部 release 写

/* 线程 B */
P = gc_load_ref(rt, t, slot);  // (3) acquire 读
P->field;                       // (4) 保证看到 (1) 的写入
```

**保证**:`gc_store_ref` 内部对 slot 的写入用 `memory_order_release`,`gc_load_ref` 用 `memory_order_acquire`。release-acquire 配对建立 happens-before:(1) → (2) → (3) → (4)。

```c
/* gc_store_ref 内部（GC_MULTITHREAD） */
atomic_store_explicit((_Atomic(gc_header*)*)slot, new_value, memory_order_release);

/* gc_load_ref 内部 */
return atomic_load_explicit((_Atomic(gc_header*)*)slot, memory_order_acquire);
```

### 3.2 STW:协调员 → mutator 挂起 → 协调员独占

```
协调员线程                          mutator 线程
─────────                          ───────────
CAS(gc_state, RUNNING→STW_REQ)
  [release]
                                   poll: load(gc_state) [acquire]
                                   看到 STW_REQ
                                   保存栈根
                                   DEC(arrive_count) [release]
                                   park（自旋 load gc_state [acquire]）
load(arrive_count)==0 [acquire]
  ← happens-before:mutator 的栈根保存对协调员可见
执行 GC（独占,无并发）
store(gc_state, RUNNING) [release]
                                   poll 看到 RUNNING [acquire] → 恢复
```

**关键**:`arrive_count` 的 DEC(release) 与协调员的 load(acquire) 配对,保证协调员开始 GC 时,所有 mutator 的栈根保存都已完成且可见。

## 4. 并发标记的三色不变式与内存序

> **符号映射（本节伪代码用到的辅助类型/函数，照抄前必读）**：
> 本节是**内存模型论证**，C 代码块重在展示内存序与 CAS 用法，其中有些辅助符号是"示意名"，真实代码里要按下表替换：
>
> | 本节示意名 | 真实出处 / 应替换为 |
> |----------|-------------------|
> | `gc_color_meta` | `GcRcMeta`（13 §2.4，含 `rc`/`gc_ref`/`color`/`in_purple`）。持有 color 和 rc 的就是同一个 meta，不是两个类型 |
> | `rc_meta_of(obj)` | 13 §2.4 的 `rc_meta_of(obj)`，返回 `GcRcMeta*` |
> | `color_of(obj)` / `is_black(obj)` / `is_white(obj)` | `rc_meta_of(obj)->color` 的比较（`== RC_COLOR_BLACK` 等，枚举见 05 §D.2） |
> | `set_color(obj, C)` / `set_gray(obj)` / `set_black(obj)` | `rc_meta_of(obj)->color = C`（并发场景用 §4.4 的 CAS `try_set_gray`） |
> | `gc_concurrent_worklist_push(rt, obj)` | 就是 `gc_worklist_push(&state->mark_worklist, obj)`（05 §F 的 `mark_worklist`），没有独立的并发 worklist API |
> | `marking_active` | `state->marking_active`（05 §E.2 的 `GcIncrementalState`，或 regional 的 `GcRegionalState.concurrent_marking`），按所用算法取 |
> | `gc_header_node` / `rt->global_head`（§6） | §6 是**无锁链表的设计示例**，非真实结构；实现时按需在 runtime 加 `gc_header_node* global_head` |
>
> **关键**：颜色和 rc 都存在 `GcRcMeta` 里（内联头法，13 §2.4），不要去找单独的 `gc_color_meta` 类型。本节的 CAS 代码改用 `GcRcMeta* m = rc_meta_of(obj);` 即可直接编译。

### 4.1 危险场景(漏标)

```
collector 正在标记                  mutator
─────────                          ───────
扫描 black 对象 A 的字段
  看到 A.x == B（白色）
  准备标记 B
                                   A.x = C   （C 也是白色,新对象）
                                   A.x 不再指向 B
  标记 B（但 B 现在不可达了,无害）
                                   ← C 没人标记！漏标！
标记结束 → C 仍是白色 → 被回收
但 A.x == C → use-after-free
```

### 4.2 写屏障修复(Incremental-Update)

```c
/* 写屏障:黑色对象新增白色引用 → 把新引用标灰 */
void write_barrier(rt, t, owner, slot, old, new) {
    atomic_store_explicit(slot, new, memory_order_release);
    if (!marking_active) return;
    if (color_of(owner) == BLACK && color_of(new) == WHITE) {
        set_color(new, GRAY);                       // CAS 或 release 写
        gc_concurrent_worklist_push(rt, new);       // 加入待扫描
    }
}
```

### 4.3 写屏障修复(SATB)

```c
/* SATB:记录被覆盖的旧值（快照时刻可达的对象都算活） */
void write_barrier_satb(rt, t, owner, slot, old, new) {
    if (marking_active && old != NULL && color_of(old) == WHITE) {
        set_color(old, GRAY);
        gc_concurrent_worklist_push(rt, old);
    }
    atomic_store_explicit(slot, new, memory_order_release);
}
```

### 4.4 颜色的原子操作

颜色变更可能被多线程并发执行(collector 标记 + mutator barrier)。必须用 CAS:

```c
/* 把对象从 WHITE 原子地变为 GRAY,返回是否成功 */
static int try_set_gray(gc_color_meta* m) {
    uint8_t expected = WHITE;
    return atomic_compare_exchange_strong_explicit(
        &m->color, &expected, GRAY,
        memory_order_acq_rel, memory_order_acquire);
}
```

## 5. RC 的原子计数

### 5.1 retain / release 的内存序

```c
/* retain:relaxed 足够（只是计数,不依赖其他数据可见性） */
static void rc_retain(gc_color_meta* m) {
    atomic_fetch_add_explicit(&m->rc, 1, memory_order_relaxed);
}

/* release:dec 到 0 时需要 acquire,确保看到所有之前的写入 */
static void rc_release(gc_runtime* rt, gc_header* obj) {
    gc_color_meta* m = rc_meta_of(obj);
    /* fetch_sub 返回旧值；旧值==1 表示这次减到 0 */
    if (atomic_fetch_sub_explicit(&m->rc, 1, memory_order_release) == 1) {
        atomic_thread_fence(memory_order_acquire);  // 确保看到对象的最终状态
        rc_reclaim(rt, obj);                        // 安全释放
    }
}
```

**为什么 release + acquire fence**:多个线程可能并发 release 同一对象。release 保证每个线程对对象的修改在 dec 前完成;最后减到 0 的线程用 acquire fence 确保看到所有其他线程的修改,然后才能安全释放。这是标准的引用计数模式(参见 C++ shared_ptr 实现)。

## 6. 全局对象链表的无锁插入

```c
/* mutator 分配后,CAS 把新对象插入全局链表头 */
void gc_global_list_push(gc_runtime* rt, gc_header_node* node) {
    gc_header_node* old_head;
    do {
        old_head = atomic_load_explicit(&rt->global_head, memory_order_relaxed);
        node->next = old_head;
    } while (!atomic_compare_exchange_weak_explicit(
        &rt->global_head, &old_head, node,
        memory_order_release, memory_order_relaxed));
}
```

> 更好的方案:TLAB 批量挂载 — 每个线程本地链表攒够一批,一次 CAS 挂到全局,减少竞争(见文档 07 §2.2)。

## 7. 内存序速查表

| 操作 | 内存序 | 理由 |
|------|--------|------|
| slot 写(发布对象) | release | 对象初始化对读者可见 |
| slot 读(读引用) | acquire | 看到完整初始化的对象 |
| rc 增 | relaxed | 纯计数 |
| rc 减 | release(+ 减到0时 acquire fence) | 安全释放 |
| color CAS | acq_rel | 颜色变更的双向同步 |
| gc_state 读(poll) | acquire | 及时看到 STW 请求 |
| gc_state 写 | release | STW 请求对所有线程可见 |
| arrive_count 减 | release | 栈根保存对协调员可见 |
| arrive_count 读(协调员) | acquire | 配对上面 |
| 全局链表 CAS | release/relaxed | 节点 next 对读者可见 |
| dirty card 标记 | relaxed(非原子也可) | 多标一次脏无害 |

## 8. 数据竞争检测

### 8.1 ThreadSanitizer 是强制门禁

多线程代码**必须**通过 TSan,任何 data race 报告都是 bug:

```bash
cmake -B build-tsan -DGC_MULTITHREAD=ON -DSAN_THREAD=ON -DCMAKE_BUILD_TYPE=Debug
cmake --build build-tsan
ctest --test-dir build-tsan --output-on-failure
```

### 8.2 TSan 常见误报与真报

| TSan 报告 | 通常是 | 处理 |
|----------|--------|------|
| slot 读写竞争 | 真报(忘了用 atomic) | 改用 atomic_load/store_explicit |
| dirty card byte 竞争 | 误报(故意非原子,多标无害) | `__tsan_acquire/release` 标注或忽略 |
| 颜色位竞争 | 真报(没用 CAS) | 改用 compare_exchange |
| stats 计数竞争 | 真报(多线程累加) | per-thread 统计后汇总,或 relaxed atomic |

## 10. 实现顺序(并发部分)

```
1. 先让单线程（GC_MULTITHREAD=OFF）完全正确
2. 启用 GC_MULTITHREAD,把所有共享访问改为 atomic（按 §7 速查表）
3. 实现 safepoint + STW（先用最简单的全局锁版本验证正确）
4. TSan 跑通
5. 再逐步把全局锁换成无锁结构（CAS 链表、work-stealing deque）
6. 每换一个,重新跑 TSan + 压力测试
```

> **黄金法则**:先正确(可以用全局大锁),再逐步无锁化。不要一开始就写无锁代码。
